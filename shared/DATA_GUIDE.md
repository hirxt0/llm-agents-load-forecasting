# Данные для эксперимента: инструкция для участников

Этот файл - для всех, кто запускает свою систему (одиночный агент, мультиагентная система, бейзлайны). Чтобы результаты можно было сравнить, **у всех должны быть одни и те же данные, одни и те же дни и одинаковый подсчёт метрик.**

> Версия 2. Выборка пересобрана: больше зданий, гигиена данных, окна по типам дней, новые метрики. Старые файлы окон (50 зданий) больше не используются.

## 1. Какие данные берём

**Источник:** бенчмарк BuildingsBench (NREL), реальные почасовые данные электропотребления, единицы - **кВт·ч за час**.

**100 тестовых зданий + 10 отладочных:**

| Группа | Датасет | Тест | Отладка | Где | Годы |
|---|---|---|---|---|---|
| Коммерческие | BDG-2 | 50 | 5 | США: Беркли (Bear), Темпе (Fox), Орландо (Panther), Вашингтон (Rat) | 2016–2017 |
| Жилые | LCL (Low Carbon London) | 50 | 5 | Лондон | 2012–2013 |

Коммерческие - офисы, учебные корпуса, общественные здания, гостиницы, магазины, склады и т.д. (столбец `btype`, площадка - `site`). Жилые - квартиры и дома с одним умным счётчиком. Среднее потребление: коммерческие ~150 кВт·ч в час, жилые ~0.25.

**Ничего скачивать не нужно.** Всё лежит в этой папке:

| Файл | Что внутри |
|---|---|
| `windows_test.parquet` | Ряды для 400 тестовых окон (история + правильный ответ) |
| `windows_dev.parquet` | Ряды для 40 отладочных окон |
| `test_windows.csv`, `dev_windows.csv` | Список окон с датами и типами дней: удобно открыть в Excel |

## 2. Что такое «окно» и какие дни прогнозируем

Одно окно - одна задача прогноза:
- **история:** 336 часов, то есть **14 суток** подряд;
- **прогноз:** следующие **24 часа**, с **00:00 до 23:00** одних суток (всегда с полуночи);
- окна одного здания не пересекаются.

У каждого здания **4 окна - по одному на тип прогнозируемых суток** (столбец `day_type`):

| `day_type` | Что за день |
|---|---|
| `weekday` | Обычный будний день |
| `weekend` | Обычный выходной |
| `holiday` | Государственный праздник (США - федеральные + штата, Великобритания - Англия) |
| `weather` | Погодная аномалия: среднесуточная температура сильнее всего отклоняется от средней за ±15 дней (верхние 5% за год) |

Так в выборке гарантированно есть особые дни, где контекст должен помогать, и результат можно разложить по типам дней.

## 3. На каком промежутке тестируем

| Группа | Прогнозы с | по |
|---|---|---|
| BDG-2 (коммерческие) | 18.01.2016 | 31.12.2017 |
| LCL (жилые) | 15.01.2012 | 29.12.2013 |

**Всего: 100 зданий × 4 окна = 400 тестовых окон.**

**Основная выборка - 200 окон** (`in_main_200 = True`): по 2 окна с каждого здания - один обычный день (будний или выходной поочерёдно) и один особый (праздник или погода поочерёдно). В ней по 50 окон каждого типа дня. **Все LLM-системы гоняем на этих 200 окнах.** Бейзлайны - на всех 400.

**Повтор - 50 окон** (`in_repeat_50 = True`) из основных, поровну по датасетам и типам дней: на них LLM-систему запускают повторно, чтобы оценить разброс между запусками.

**Отладка - 40 окон 10 других зданий** (`windows_dev.parquet`): только для настройки промптов и параметров. Тестовые окна для настройки не используем.

## 4. Формат файлов parquet

Одна строка - один час одного окна.

| Столбец | Что это |
|---|---|
| `building_id` | Здание и год, например `Bear_assembly_Danial@2017` или `MAC000708@2013` |
| `dataset` | `BDG-2` или `LCL` |
| `site` | Площадка: `Bear`, `Fox`, `Panther`, `Rat` или `LCL` |
| `btype` | Тип здания (`office`, `education`, ..., `residential`) |
| `window_id` | Номер окна у здания: 0 - weekday, 1 - weekend, 2 - holiday, 3 - weather |
| `day_type` | Тип прогнозируемых суток |
| `step` | Час относительно начала прогноза: **от −336 до −1 - история, от 0 до 23 - прогнозируемые сутки** |
| `timestamp` | Дата и время: BDG-2 - постоянное местное время без перехода на летнее, LCL - GMT |
| `y_clean` | **Потребление, кВт·ч. Его прогнозируем, по нему считаем ошибку** |
| `in_main_200`, `in_repeat_50` | Входит ли окно в основную выборку / в повтор (только тест) |

```python
import pandas as pd

w = pd.read_parquet("shared/windows_test.parquet")
main = w[w.in_main_200]
for (b, i), win in main.groupby(["building_id", "window_id"]):
    win = win.sort_values("step")
    history = win[win.step < 0][["timestamp", "y_clean"]]   # 336 часов - это видит система
    truth = win[win.step >= 0].y_clean.to_numpy()           # 24 часа - только для подсчёта ошибки
```

## 5. Что уже сделано с данными (гигиена)

- **Отбор зданий:** без пропусков; нулевых часов меньше 1%; значение не «залипает» дольше 12 часов; доля заполненных при очистке часов (4+ точки подряд на одной прямой - след линейной интерполяции) меньше 1%; у жилых - полный год и среднее не меньше 0.05 кВт·ч. Из 1078 рядов BDG-2 прошли 831, из LCL - 580; дальше здания взяты случайно, у коммерческих - поровну по площадкам и разным типам зданий.
- **Окна:** в прогнозируемых сутках **нет ни одного заполненного часа** (ошибку считаем только по реальным данным), в истории заполненных часов не больше 2%.
- **Время:** проверено, что нагрузка и погода выровнены. Температура достигает максимума в 14–16 ч, пик офисов приходится на 11–14 ч. Погода Лондона приведена к GMT, как и нагрузка.
- Здания отладки и теста не пересекаются.

**Правила для вашей системы:**
1. **Системе даём только историю** (`step < 0`). Значения `step >= 0` нельзя показывать ни агенту, ни инструментам, ни использовать для подбора параметров.
2. **Не берём данные вне окна:** ни другие окна того же здания, ни другие даты.
3. **Ряд не чистим:** данные уже очищены.
4. **Нормализацию**, если она нужна, считаем только по истории окна; прогноз сдаём в кВт·ч.
5. **Прогноз:** ровно 24 неотрицательных числа на часы 00–23.
6. **Названия зданий LLM не показываем:** только обезличенный код (`anon_id` из `src/context.py`), иначе модель может «вспомнить» здание из открытых данных.

## 6. Если система использует внешний контекст

Погоду, праздники, сведения о здании и новости брать **теми же функциями, что у одиночного агента** (`src/context.py`), иначе сравнение нечестное:

| Контекст | Как | Функция |
|---|---|---|
| Сведения о здании | Тип, площадь, год постройки, климат; без названия и города | `building_info(building_id)` |
| Праздники | Библиотека `holidays` по стране и штату | `holiday_name(building_id, day)` |
| Погода | История - факт. **На день прогноза - «прогноз погоды» с ошибкой**: от 1 °C в начале суток до 2 °C в конце, ночью и зимой больше; зерно фиксировано, ошибка у всех одинаковая | `weather(building_id, ts_hist, ts_future, mode="noisy", key=(building_id, str(origin)))` |
| Новости | Портал «Current events» Википедии в версии страницы **на момент за 1 час до начала прогноза** | `news(day, origin, query, utc_offset=SITES[site]["utc_offset"])` |

Для этих функций нужны исходные файлы в `data/raw/` - см. README.

## 7. Метрики и формат сдачи

**Метрики (версия 2)** - все считаются одной функцией `forecast_metrics(y_true, y_pred, history)` из `src/metrics.py`:

| Метрика | Что это | Роль |
|---|---|---|
| **NRMSE, %** | RMSE / среднее за 14 суток истории × 100 (CV(RMSE), как в BuildingsBench) | **Основная** |
| NMAE, % | MAE / среднее истории × 100 | Дополнительная |
| MASE | MAE / ошибка прогноза «как вчера» на истории; < 1 - лучше «как вчера» | Дополнительная |
| NMBE, % | Среднее (прогноз − факт) / среднее истории × 100; > 0 - завышение | Систематический сдвиг |
| MAE, RMSE | В кВт·ч, только внутри одного датасета | Для наглядности |
| MAPE, % | Только для коммерческих зданий: у домов потребление бывает около нуля (20% часов < 0.05 кВт·ч), там MAPE не определена | Вторичная |

**Агрегирование и тесты** (делает `src/summarize.py`):
1. Метрика считается по каждому окну, затем **усредняется внутри здания**, затем берётся **медиана по зданиям** - отдельно для BDG-2 и LCL.
2. Сравнение двух систем: отношение NRMSE по зданиям (геометрическое среднее), **95% ДИ кластерным бутстрепом по зданиям**, Wilcoxon по зданиям, **поправка Холма** на все сравнения.
3. Отдельно - разбивка по типам дней.

**Формат сдачи прогнозов** - `results/<префикс>_<название>_test/predictions.csv`, одна строка на час:
```
building_id,window_id,hour,y_true,y_pred
Bear_assembly_Danial@2017,0,0,61.23,59.87
```
Префиксы: `fc_` - одиночный агент, `ma_` - мультиагентная система, `bl_` - бейзлайны. Для LLM-систем рядом - `scores.csv` по окнам: токены (вход, выход, reasoning), число вызовов LLM, секунды, стоимость, `failed` (не удалось сдать прогноз - подставляется «как вчера», сбой считается отдельно).

**Ориентиры** (основные 200 окон, медиана по зданиям):

| | NRMSE | NMAE | MASE | MAE, кВт·ч | MAPE |
|---|---|---|---|---|---|
| BDG-2, «как вчера» | 8.8% | 7.2% | 0.89 | 5.53 | 7.5% |
| BDG-2, «как неделю назад» | 14.0% | 11.3% | 1.31 | 9.16 | 10.8% |
| LCL, «как вчера» | 84.9% | 55.3% | 0.97 | 0.10 | - |
| LCL, «как неделю назад» | 89.0% | 55.7% | 0.96 | 0.10 | - |
