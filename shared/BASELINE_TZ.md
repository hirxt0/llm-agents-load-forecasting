# ТЗ: бейзлайны для сравнения с LLM-агентами

**Исполнитель:** участник, отвечающий за бейзлайны.
**Зачем:** без сильных классических моделей и foundation-моделей рецензент не примет вывод «агент лучше/хуже». Задача - дать честную планку, которую агенты должны перепрыгнуть, на тех же окнах и при той же доступной информации.

Данные, окна и метрики описаны в `shared/DATA_GUIDE.md` - сначала прочитать его.

---

## 1. Что прогнозировать

- Все **400 тестовых окон** из `shared/windows_test.parquet` (бейзлайны дешёвые, считаем на всех). В отчёте отдельно приводятся результаты на основных 200 (`in_main_200`), чтобы было видно, что ранжирование на подвыборке совпадает с полной.
- Каждое окно: 336 часов истории (`step < 0`) -> 24 часа прогноза (`step 0..23`), целевая колонка `y_clean`, кВт·ч.
- Гиперпараметры подбирать **только на** `shared/windows_dev.parquet` (40 окон других зданий). На тестовых окнах ничего не настраивать.

## 2. Правило равной информации

Бейзлайн не должен видеть больше или меньше, чем агент в сопоставимой конфигурации.

| Информация | Можно использовать | Как получить |
|---|---|---|
| История ряда | Только 336 часов своего окна | `step < 0` |
| Календарь | Час, день недели, флаг праздника | `context.holiday_name(building_id, day)` |
| Температура за историю | Фактическая | `context.weather(...)` -> первая часть ответа |
| Температура на день прогноза | **Только «прогноз погоды» с ошибкой**, не факт | `context.weather(building_id, ts_hist, ts_future, mode="noisy", key=(building_id, str(origin)))` |
| Другие окна, другие здания, будущее | **Нельзя** | - |

Функции из `src/context.py` дают ровно ту же погоду с той же ошибкой (фиксированное зерно), что и у агентов. Для них нужны исходные файлы в `data/raw/` (см. README, раздел «Данные»).

## 3. Список бейзлайнов

### Обязательные

| Имя папки | Модель | Детали |
|---|---|---|
| `bl_snaive_24` | Как вчера | Значения последних 24 ч истории |
| `bl_snaive_168` | Как неделю назад | Значения того же дня неделю назад |
| `bl_persistence_ens` | Persistence Ensemble из BuildingsBench | Точное определение взять из кода BuildingsBench (github.com/NatLabRockies/BuildingsBench); если оно там не найдётся - среднее того же часа за предыдущие 7 суток. По опубликованным результатам на жилых зданиях он сильнее foundation-моделей |
| `bl_ets` | AutoETS, сезон 24 | `statsforecast` |
| `bl_mstl` | MSTL, сезоны [24, 168], тренд AutoETS | `statsforecast` |
| `bl_lgbm` | LightGBM без погоды | Локально по окну: лаги 24/48/72/168, среднее за предыдущие сутки, час, день недели, флаг праздника. Прогноз напрямую на 24 ч (все лаги ≥ 24) |
| `bl_lgbm_weather` | LightGBM с погодой | То же + температура (история - факт, день прогноза - `noisy`) |
| `bl_chronos_bolt` | Chronos-Bolt (base), zero-shot | Медиана прогноза; только история |
| `bl_chronos2` | Chronos-2, zero-shot | Без ковариат |
| `bl_chronos2_weather` | Chronos-2 с температурой | Температура как ковариата: история - факт, будущее - `noisy` |
| `bl_timesfm` | TimesFM 2.x (последняя открытая версия), zero-shot | Контекст 336, горизонт 24 |

### Желательные

| Имя папки | Модель | Детали |
|---|---|---|
| `bl_bb_transformer` | Предобученный Transformer-L из BuildingsBench, zero-shot | Его родной контекст 168 ч - передать последние 168 ч и указать это |
| `bl_automl` | Выбор модели по backtest | Из обязательных моделей выбрать лучшую по MAE на последних 2 сутках истории |
| `bl_moirai` | Moirai, zero-shot | Для полноты картины |

Все foundation-модели запускаются локально (CPU/GPU), API не нужен.

## 4. Проверка на утечку у foundation-моделей

Foundation-модели могли видеть наши данные при предобучении: в открытые обучающие корпуса временных рядов входят наборы с умными счётчиками Лондона и данными зданий.

**Задача:** по статьям и карточкам моделей (Chronos, Chronos-2, TimesFM, Moirai/LOTSA, BuildingsBench) выяснить, входят ли в их обучающие данные **BDG-2 / Building Data Genome**, **Low Carbon London / London Smart Meters** или **BuildingsBench**. Итог - таблица «модель -> есть пересечение / нет / неизвестно, со ссылкой». Это раскрываем в статье.

## 5. Формат сдачи

Для каждого бейзлайна - папка `results/bl_<имя>_test/` (и `results/bl_<имя>_dev/` для отладки):

**`predictions.csv`** - одна строка на час:
```
building_id,window_id,hour,y_true,y_pred
Bear_assembly_Danial@2017,0,0,61.23,59.87
```

**`run_info.json`** - модель и версия (точное имя чекпойнта), параметры, что подавалось на вход (история / календарь / погода), железо, общее время и среднее время на окно, дата запуска.

После этого `python summarize.py --split test` сам добавит бейзлайны в общую таблицу, посчитает все метрики и сравнения с агентами.

## 6. Метрики и проверка

- Метрики не считать самостоятельно - их считает общая функция `forecast_metrics` из `src/metrics.py` (NRMSE основная; NMAE, MASE, NMBE, MAE, RMSE; MAPE только для коммерческих). Своя проверка - через `summarize.py`.
- Санити-чек: у `bl_snaive_24` на основных 200 окнах медианный NRMSE должен быть около **8.8%** (коммерческие) и **85%** (жилые). Если не так - ошибка в выравнивании окон.
- Прогноз - ровно 24 неотрицательных числа (отрицательные обрезать до 0). Если модель упала на окне - подставить `bl_snaive_24` и записать это в `run_info.json`.

## 7. Результат работы

1. Папки `results/bl_*_test/` и `results/bl_*_dev/` для всех обязательных бейзлайнов.
2. Таблица пересечения обучающих корпусов (раздел 4).
3. Короткая заметка: версии моделей, что не получилось и почему.

Код бейзлайнов - в `src/baselines/` (по файлу на группу моделей), чтобы его можно было перезапустить одной командой.
